# Reeden 同步插件

把 [Reeden](https://reeden.app)（Android 阅读器）的阅读数据从 WebDAV / S3 上读回来，导入本服务器：**阅读进度、阅读时长、书目信息、封面**。

Reeden 自身没有开放同步协议，但它在自己的根目录里留了一份完整的数据。这个插件就是把那份数据读出来 —— **只读，绝不改动**你的 Reeden 目录。

---

## 一、Reeden 在它的目录里留了什么

| 路径 | 内容 |
|---|---|
| `metadata` | zip，含 `book.json`（书目）、`read_record.json`（阅读会话）、`read_record_hourly.json`（按小时的阅读时长）等 |
| `book_progress/<bookId>.json` | 每本书的阅读位置：章节、段落、百分比、最后阅读时间、设备 |
| `covers` | zip，里面是 `<hash>.thumb` 封面图，`book.json` 的 `cover_thumb` 指向它们 |

`metadata` 与 `covers` 是**没有扩展名的 zip**，`book.json` 里的 `title` / `author` 是 UTF-8 中文。

### 三条数据源的取舍

这几条是从真实导出里核对出来的，直接决定了导入对不对：

- **进度**：取 `book_progress/<id>.json` 与 `book.json` 的 `last_read_time` 里较新的那个。
  `readProgress` 是 0–10000 的整数（`8592` = 85.92%），导入后按服务端口径换算。
- **时长**：优先 `read_record_hourly.json`，它的「书 + 日期 + 小时」粒度与本服务器的
  `reading_sessions` 完全对得上；`read_record.json` 是同一批数据的「会话」视图
  （时长记在开始的那一小时），但它**多出更早的若干天**，所以两份都读：
  hourly 覆盖到的日子用 hourly，其余日子按 `read_record` 的 `create_at` 归到对应小时。
- **两份绝不能相加。** 实测同一「书 + 日期」的日总数两边完全一致，相加会把时长翻倍
  （样本里会从 159202 秒变成 311791 秒）。这正是端到端验证里那条断言在守的东西。
- `book_progress` 里的 `todayStats` **不用**：它只覆盖当天一小段窗口，且会被轮转，
  而 hourly / record 是完整的。

### 时间戳口径

`read_record_hourly.json` 里的 `date` / `hour` 是**本地时间**，而 `read_record.json` 的
`create_at` 是 **UTC**。插件按「时区偏移」配置项换算（默认 +8），否则整天的时长会落到
错误的小时上、热力图会乱。这个偏移是从样本中核对出来的：按 +8 换算后，
两份数据的小时归属能逐条对上。

## 二、准备工作

1. 确认 Reeden 的根目录已经同步了出去（Reeden 自带的 WebDAV / S3 备份）。
2. 管理员把插件装上、启用。
3. **每个要用的人**在自己账号里填一份配置（设置 → 插件）：网盘地址、凭据、根目录。
   导入的数据只会进他**自己的账号**。

**不需要**为了它在「存储管理」里建一条存储条目 —— 连接信息直接填在插件配置里。
Reeden 的同步目录往往与书籍文件存储不是同一个地方（不同网盘、不同桶，或者
干脆是服务器上的一个目录），把它绑到书库存储上只会让两边都变别扭。

> 想让插件复用「存储管理」里已经配好的那条存储也可以：把「Reeden 数据放在哪」
> 选成「复用已有存储」，再填存储 ID（只能填自己的存储）。

## 三、安装与配置

```bash
# 打包并安装（在仓库根目录）
cd packages/server/plugins-samples/reeden-sync
zip -r /tmp/reeden-sync.zip .        # 注意：plugin.json 与 index.js 必须在 zip 根部
cd -
readsync plugin:install /tmp/reeden-sync.zip
readsync plugin:enable com.readsync.reeden-sync
```

也可以在**管理后台 → 插件**里上传 zip、启用。

**配置是分层的**：管理员只定全站的节奏，其余都在每个用户手上。

| 配置项 | 谁填 | 说明 |
|---|---|---|
| 自动导入间隔 | 管理员 | 分钟；填 `0` 表示只在手动触发时导入 |
| 每日固定同步时间 | 管理员 | 默认 `23:55`；留空关闭 |

下面的都在**设置 → 插件**里由每个用户自己填（表单会按选择只显示相关字段）：

| 配置项 | 说明 |
|---|---|
| Reeden 数据放在哪 | 「在这里填连接信息」（默认）或「复用已有存储」 |
| 连接方式 | WebDAV / S3 兼容对象存储 / 服务器本地目录 |
| WebDAV 地址、用户名、密码、根目录、允许自签名证书 | 选了 WebDAV 时出现。坚果云这类服务要用**应用密码**而不是登录密码 |
| S3 Endpoint、存储桶、区域、Access Key、Secret Key、对象前缀、path 风格寻址 | 选了 S3 时出现。阿里云 OSS / MinIO 要开 path 风格，Cloudflare R2 关掉即可 |
| 本地目录 | 选了本地时出现。**相对**服务器数据目录下的 `storage`，例如 `reeden` 指 `<数据目录>/storage/reeden`（本地驱动不允许绝对路径） |
| 已有存储的 ID | 选了「复用已有存储」时出现；只能填自己的 |
| Reeden 根目录 | 上面那个位置之下的 Reeden 根目录；留空表示就是它本身 |
| 进度目录名 | 默认 `book_progress`（有些版本是 `bookprogress`） |
| 时间戳时区偏移 | 默认 `8`；只影响那些 hourly 没覆盖到的早期数据 |
| 自动登记缺失的书目 | 默认开；关掉后只导入已在书库里的书 |
| 导入阅读时长 / 取封面 | 默认都开 |

密钥类字段（密码、Access Key、Secret Key）与其他凭据一样**加密落库**，页面上只回显掩码；
**每个用户只能看到、也只能改自己那份**。

配置改完**立即生效**，不必重启服务。

### 为什么没有「导入到哪个账号」这一项

早先有，现在删了。那不是一个方便省事的配置项，而是一个越权口子：谁都可以在自己
的配置里写上别人的用户名，把数据导进别人的账号。现在导入的目标账号由服务端在
`ctx.forUser(userId)` 那一刻定死，插件的写入入口里根本没有 `user` 参数 —— 想写错
都写不了。谁是「他自己」，由登录状态决定。

插件会遍历「已经填过配置的人」，一个个导入：某个人网盘连不上只跳过他自己，
其他人照常。

## 四、跑一次

三种触发方式，都不必等定时：

| 在哪 | 跑谁 |
|---|---|
| **设置 → 插件 → 立即同步** | **只有你自己** —— 配置里写着你的网盘地址，就只同步你的账号 |
| **管理后台 → 插件 → 立即运行** | 所有配置过的账号 |
| `readsync plugin:run com.readsync.reeden-sync` | 同上（命令行） |

```bash
# 命令行：任务名可省略，默认取 sync
readsync plugin:run com.readsync.reeden-sync

# 看插件任务有哪些
readsync plugin:list
```

「设置 → 插件」页面上会显示上次运行的结果（导入了多少本书、多少条进度、多少段时长），
点完「立即同步」也会直接把这次的结果弹出来。

> 同一个人连着点两次不会重复跑：第一次还在跑的时候，第二次会收到「正在运行中」。

## 五、导入之后

- 每本书的**文档标识取自 Reeden 的 `bookId`**：`bookId` 本身就是 32 位十六进制时
  （常见情况）原样使用，于是网页上那串标识与 Reeden 里的值完全一致，对不上时可以直接核对；
  不是十六进制时（UUID 形式的库）会派生一个稳定的键 —— 服务端只接受十六进制标识，
  直接把 `bookId` 塞进去会被拒，一本书都导不进来。
- 阅读进度会出现在**书籍详情页**，阅读状态会自动从「未读」推进到「在读」。
- 阅读时长进入**统计**：趋势、热力图、阅读时长都包含这部分。
- 封面来自 Reeden 的 `covers`。**只给这次导入新建的书设置封面** ——
  你后来自己传过封面的书不会被覆盖。
- 平台标识是 `reeden`。想让它显示成中文名，可在**设置 → 阅读平台管理**里加一个
  id 为 `reeden` 的平台。

## 六、它为什么可以反复跑

导入是**幂等**的，定时任务会在后台一直跑，所以这点必须成立：

| 数据 | 幂等方式 |
|---|---|
| 书目 | 按 `bookId`（即文档标识）与 MD5 去重，已存在就复用 |
| 进度 | 走服务端统一同步接口的 upsert，同一文档只保留最新 |
| 时长 | **按天替换**：每次导入都先删掉该账号 + `reeden` 平台 + 这些天的旧行，再写入 |
| 封面 | 只对新建的书设置一次 |

「按天替换」还顺带处理了上游删除：插件记着上次导入过哪些天，这次没出现的天会被
清空，不会在本地留下早已不存在的数据。

### 上游没变就整轮跳过

默认开启（管理员可在插件配置里关掉）。每跑一次，插件**先只读元信息**：
`metadata` 与 `book_progress/` 下每个文件的大小与修改时间，再和上次的拼成一个指纹。

一样就直接返回「上游没有变化，无需导入」—— **一个字节都不下载、库里一条记录都不写**，
连上次运行记录都不刷新。定时每小时的同步绝大多数趟都走这条路。

两点值得知道：

- **不只看大小。** 进度从 `5000` 变成 `5001` 长度一模一样，只有修改时间会变。
  （这条有专门的验证，见下一节。）
- **指纹里带「导入逻辑版本」。** 插件改了导入逻辑就把它 +1，让所有用户下次完整重跑
  一遍刷新历史数据。否则修好的逻辑对老数据不生效，用户只会看到「升级了但没变化」。

### 只重写变了的那部分

整轮跳过管的是「什么都没变」。只要有一本书读了，就轮到第二层筛选：

- **进度**：与服务器上那份（位置 + 百分比）一致就不推。上游的 `last_read_time`
  经常自己往前走（打开一次书、同步一下就变了），照推的话服务端会接受并重写这本书的
  「最近阅读 / 最近更新」—— 表现出来就是**只有一本书在读，书库里所有书都显示成刚更新过**。
- **时长**：按天算指纹，只发「变了的天」和「上游已经没有的天」。服务端的时长导入是
  **先删后写**，整批发等于把所有书、所有天的记录都重写一遍。

这两条的效果会写进「上次运行」那句话里，例如
`进度 3 条（12 本没变，未重写），时长 1 段` —— 一眼能看出这轮到底动了多少东西。

## 七、验证

仓库里带一份端到端验证脚本，需要你自己提供一份 Reeden 导出：

```bash
cd packages/server
READSYNC_DATA_DIR=./data-reeden REEDEN_SAMPLE=/path/to/你的/Reeden \
  npx tsx src/scripts/reeden-import-check.ts
```

仓库里**不附带**样本：Reeden 的导出是真实的阅读数据（书目、阅读时长、划线标注），
不该躺在公开仓库里。脚本**只读**你给的那个目录，不会改动它。

它会真的安装插件（走 zip 校验）、真的读 zip、真的写库，然后核对**从样本里独立算出来的**
数字：书目数、会话行数、总秒数、单日秒数、进度百分比、封面，以及三种数据源各跑一遍、
「重跑一遍结果不变」。

三种数据源各用一个**独立账号**，每个账号配自己那份配置 —— 于是下面这些能真的断言，
而不是靠人眼看日志：

- 只配了一个人时，另外两个账号一本书都不会多；
- 三个账号的配置互不串台（S3 那个读到的是自己的桶，本地那个仍是本地目录）；
- S3 的密钥不会漏进别人的配置里。

注意那些期望值（18 本书、159202 秒、单日 8447 秒…）是**按某一份具体导出算出来的**：
换一份数据跑时它们要对你的导出重新算过。这个脚本守的是「导入逻辑与样本口径一致」，
不是「所有导出都长这样」。

### 不需要样本的那份（上游没变就跳过）

「没变就跳过」这条逻辑一旦失效，用户看到的是「同步跑过了但数据没更新」，比不跳过
还难排查，所以它单独有一份**自造数据源**的验证 —— 不依赖任何样本：

```bash
cd packages/server
READSYNC_DATA_DIR=./data-reeden-skip npx tsx src/scripts/reeden-skip-check.ts
```

它自己造一棵与 Reeden 导出同构的目录树（`metadata` zip + `book_progress/*.json` +
`covers` zip），然后走真实内核：装插件 → 配好 → 触发任务 → 校验。

断言里有两条是特意为「跳过」设计的：

- **「跳过那一轮库里一个字节都没动」** —— 对比运行前后的整库快照。为了证明这个探针
  不是碰巧通过，同一份脚本还有一条反向断言：把跳过关掉后全量重跑，快照**必须**变。
- **「内容变了、长度没变」的进度文件也必须被发现** —— 这条专否「只比大小」的实现。

## 八、常见问题

**导入后时长对不上，比 Reeden 里显示的多**

检查是否只导入了 hourly 与 record 中的一份（两份相加会翻倍）。本插件默认按「hourly 优先、
record 补缺」处理，两者不会同时计入同一天。

**热力图上的时间点不对**

「时间戳时区偏移」没配对。hourly 里的时间是本地时间，record 里的是 UTC；
如果你的时区不是东八区，把它改成你的实际偏移。

**书都被登记了，但我只想导入已有的书**

关掉「自动登记缺失的书目」。这时只会导入按文档标识能在书库里找到的书，
其余会被计入「跳过」并在日志里体现。

**一本书都没导入**

先看日志（设置 → 插件 页面上也会显示每个账号上次运行的结果）。常见原因：

- **你自己那份配置还没填。** 插件只处理「已经保存过配置的人」，谁都没配就什么
  都不做。
- 本地目录写成了绝对路径。本地驱动只接受**相对** `<数据目录>/storage` 的路径。
- WebDAV 地址没填到能直接列目录的那一层，或者用了登录密码而非应用授权码。
- 连接参数不对时插件会**在导入开始前**就报「存储连接不可用」并给出原因，
  可以先按那条提示排查。某个人的配置有问题只会跳过他自己，不影响其他人。

**旧的「导入到哪个账号」配置项不见了**

1.1.0 → 1.2.0 的改动：账号不再由配置决定（见上文「为什么没有……」）。升级后每个
用户要在「设置 → 插件」里填一次自己的网盘信息。

**一次都没跑起来（管理员视角）**

管理员那侧只剩「自动导入间隔」和「每日固定同步时间」。若间隔填了 `0`，插件不会
自己跑，需要手动触发：

```bash
readsync plugin:run com.readsync.reeden-sync
```

**Reeden 目录里没有 `read_record.json`**

不影响：hourly 与「进度 + 书目」照样能导入，只是早期那些天没有时长数据。

**装了新版提示「apiVersion 不满足」**

- **1.4.0** 起：进度与时长都要「先跟服务器比一比再写」，用到内核的
  `ctx.sync.getProgress` 与插件存储的修改时间，要求服务端 **≥ 0.4.8**。
- **1.3.0** 起：跳过判断要用到文件修改时间，要求 **≥ 0.4.6**。

先把服务端升级再装插件。**升级服务端之后**，插件的下一轮会完整重跑一次
（指纹键里带着导入逻辑版本），这是预期内的。

**明明读了几页，为什么说「上游没有变化」**

先确认 Reeden 自己**已经把这次阅读同步到网盘**了（它的「同步」按钮 / 自动同步）。
插件只读网盘上那份数据：网盘还没更新，再跑也不会看到变化。若确实同步过，把
「上游没有变化时跳过」关掉再点一次「立即同步」，看是否变成正常的导入计数 ——
是的话请把日志和 Reeden 版本反馈过来。
